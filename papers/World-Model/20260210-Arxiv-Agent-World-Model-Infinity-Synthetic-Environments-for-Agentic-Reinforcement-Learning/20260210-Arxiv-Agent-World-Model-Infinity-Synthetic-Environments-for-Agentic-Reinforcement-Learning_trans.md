## 摘要

**大语言模型（Large Language Models, LLMs）** 的最新进展使得自主智能体能够执行需要与工具和环境进行多轮交互的复杂任务。然而，此类智能体训练的扩展受到 **多样化且可靠环境** 匮乏的限制。本文中，我们提出了 **智能体世界模型（Agent World Model, AWM）** ，一个完全 **合成环境生成流程** 。利用此流程，我们扩展到了覆盖日常场景的 **1,000 个环境** ，智能体可以在其中与丰富的工具集（平均每个环境 35 个工具）交互并获得高质量的观测。值得注意的是，这些环境是 **代码驱动** 的并由数据库支持，相比由 LLMs 模拟的环境，能提供更可靠和一致的状态转移。此外，与从真实环境中收集轨迹相比，它们能实现更高效的智能体交互。为了证明此资源的有效性，我们为多轮工具使用智能体进行了 **大规模强化学习** 。得益于完全可执行的环境和可访问的数据库状态，我们还可以设计可靠的奖励函数。在三个基准测试上的实验表明， **仅在合成环境中训练** ，而非在特定于基准测试的环境中训练，能产生强大的 **分布外泛化** 能力。代码发布于 [https://github.com/Snowflake-Labs/agent-world-model](https://github.com/Snowflake-Labs/agent-world-model)。

## 1 引言

**大语言模型（Large Language Models, LLMs）** 在指令遵循、推理、代码生成和工具使用方面取得了显著性能（Chen et al., 2021; Schick et al., 2023; OpenAI, 2025; Anthropic, 2025a; Comanici et al., 2025; Guo et al., 2025）。由 LLMs 驱动的 **智能体（Agents）** 成为处理现实环境中多步骤复杂任务的一个有前景的范式（Nakano et al., 2021; Yao et al., 2023; Yang et al., 2024; Qin et al., 2024）。然而，训练此类智能体通常需要在多样化的环境中进行 **大规模强化学习（Reinforcement Learning, RL）** ，而这些环境相对资源稀缺且扩展成本高昂。

使用真实世界环境进行训练成本极高且难以扩展，因为许多场景不提供公共 API，并且 RL 训练通常要求智能体以稳定高效的方式与环境交互数千次（Dulac-Arnold et al., 2021; Qin et al., 2024; Xu et al., 2024a; Luo et al., 2025）。人工创建的环境难以扩展且往往缺乏多样性。例如，$\tau^{2}$-bench (Barres et al., 2025) 和 TheMCPCompany (Esfandiarpoor et al., 2025) 分别只包含三个和五个环境，这对于训练通用 AI 智能体来说远远不够。现有大多数关于智能体的合成研究主要集中在 **任务合成** （Wang et al., 2023; Chen et al., 2024; Xie et al., 2025; Patil et al., 2024; Wang et al., 2026）和 **轨迹收集** （Xu et al., 2024b; Li et al., 2025a; Song et al., 2024），而非 **环境合成** 。另一研究方向模拟工具响应甚至整个环境，其中每个状态转移都由 LLMs 生成（Liu et al., 2024b; Lu et al., 2025; Li et al., 2025b, c; Chen et al., 2025）。然而，由于 **幻觉问题** （Wang et al., 2024; Kalai et al., 2025）和 LLM 的高推理成本，这种方法并不可靠或高效。

这些局限性凸显了一个缺失的部分： **可扩展的环境合成** 。具体而言，挑战在于大规模合成 **可执行的、可靠的环境** ，以实现可复现的智能体交互和学习。最近几个月，DeepSeek-V3.2 (DeepSeek-AI et al., 2025) 引入了一个合成流程，为通用智能体创建了数千个可执行环境，而 Qwen Tongyi (Fang et al., 2025) 也描述了一个环境合成流程，但用于 **监督微调（Supervised Fine-Tuning, SFT）** 而非 RL 训练。所采用的基于代码的方法有望大规模构建此类环境，因为它可以控制状态转移并确保环境的一致性。然而，两者均未发布其生成流程或开源其环境。一些并行的社区工作（Feng et al., 2025; Sullivan et al., 2025; Cai et al., 2025; Zhang et al., 2025a; Song et al., 2026）探索了通过编程进行环境合成。然而，它们要么针对类游戏环境，要么依赖于人类先验知识（例如代码文档），要么缺乏对状态一致性的强保证，要么在规模上仍然有限。

为了解决这个问题，我们提出了 **智能体世界模型（Agent World Model, AWM）** ，一个开源的、可大规模合成可执行工具使用环境的流程。关键洞见在于，智能体环境共享一个共同结构：一个有状态的后端、一个工具接口层和特定于任务的成功标准。通过将合成分解为这三个组件，我们可以利用 LLMs 系统地生成每个部分，同时保持一致性。我们的 AWM 反映了软件在实践中的构建方式。从高级场景描述（例如“一个在线购物平台”）开始，我们首先生成用户在此场景中可能执行的常见用户需求（即任务）。然后，我们生成 **数据库模式（Database Schema）** 来定义存在哪些实体和关系以满足这些用户需求。此模式可以指导暴露接口（工具集）的设计，并帮助生成接口的后端代码，确保每个工具都有清晰的数据模型可供操作。接口通过 **模型上下文协议（Model Context Protocol, MCP）** (Anthropic, 2024) 暴露，以实现智能体与环境的统一工具交互。最后，我们生成 **验证代码** ，比较智能体执行前后的数据库状态，这增强了一个 **LLM-as-a-Judge** ，为 RL 训练提供稳健的奖励信号。至关重要的是，每个阶段都包括自动执行和简单的自我纠正：如果生成的代码无法运行，我们会将错误信息反馈给 LLM 进行修正。

此流程使我们能够扩展到 **1,000 个独特的环境** ，涵盖大多数现实世界场景，如购物、社交媒体、金融和旅行。每个环境都提供一个可执行的沙箱，智能体可以与数十个工具交互，并且它们完全支持并行隔离实例，易于重置或重启，这对于高效的在线 RL 非常重要。为了验证 AWM，我们进行了 **大规模 RL** （每一步有 1,024 个环境实例）来训练智能体使用 MCP 工具完成任务。与一些在测试环境中进行训练的工作不同，我们的环境和任务并非为任何基准测试或特定场景量身定制。在三个工具使用基准测试上的实验结果证明了我们框架的 **泛化性能** 。总之，我们的贡献有三方面：(1) **AWM** ，一个用于自动生成具有数据库支持状态一致性的可执行工具使用环境的开源流程；(2) **1,000 个** 适用于大规模 RL 训练的即用型多样化环境；(3) 实证结果表明，在 AWM 上训练的智能体能泛化到 **分布外环境** 。

## 2 相关工作（Related Work）

**工具使用智能体（Tool-use Agents）** 。近期研究表明，大型语言模型（Large Language Models, LLMs）可以利用外部工具解决复杂任务（Qin et al., 2024; OpenAI, 2025; DeepSeek-AI et al., 2025; Team et al., 2025）。Toolformer（Schick et al., 2023）通过监督学习训练工具使用型 LLMs。ToolLLM（Qin et al., 2024）整理了真实世界的 API 并在 LLM 生成的轨迹上进行训练，但使用模拟响应而非实际执行工具。Gorilla（Patil et al., 2024）利用 API 文档进行微调以提高工具使用的准确性。ReAct（Yao et al., 2023）和 SWE-agent（Yang et al., 2024）在交互环境中交替进行推理与行动。然而，大多数训练数据仍然是静态的或来自小规模环境。现有的基准测试（Yao et al., 2024; Barres et al., 2025; Esfandiarpoor et al., 2025; Luo et al., 2025; Fan et al., 2025; Mo et al., 2025）要么使用真实世界的 API，要么提供小规模环境。这使得它们难以用作大规模强化学习（Reinforcement Learning, RL）的训练场。 **核心差距在于缺乏足够多样化、可执行且对 RL 训练足够高效的环境** 。此类训练需要智能体进行大量交互，并从快速交互和可靠的状态转换中获益。

**智能体数据合成（Agent Data Synthesis）** 。合成数据被广泛用于扩展智能体训练（Patil et al., 2024; Schick et al., 2023; Qin et al., 2024; Liu et al., 2024b, 2025）。Self-Instruct（Wang et al., 2023）推广了使用 LLMs 生成微调数据的方法。后续工作使用 LLMs 来合成任务、工具规范和智能体轨迹（Xie et al., 2025; Xu et al., 2024b; Li et al., 2025a; Song et al., 2024; Liu et al., 2024b, 2025; Wang et al., 2026; Prabhakar et al., 2025）。这些方法提供了多样化的任务和工具使用演示，但 **并未提供用于智能体交互的可执行环境** 。关键限制在于它们将环境视为给定的，或者使用 LLMs 模拟工具响应。没有环境合成，智能体就无法探索替代行动或从状态变化中获得基于现实的反馈，这限制了其在 RL 中的适用性。

**环境合成（Environment Synthesis）** 。随着智能体强化学习的发展，对多样化、可执行环境的需求变得更加迫切。环境合成主要遵循两个方向： **基于 LLM 的模拟** （Wang et al., 2024; Li et al., 2025c; Chen et al., 2025; Li et al., 2025b）和 **基于编程的合成** （Tang et al., 2024; Sullivan et al., 2025; Cai et al., 2025; Zhang et al., 2025a; Song et al., 2026）。基于 LLM 的模拟通常通过提示推理模型生成状态转移和观察来模拟环境。然而，它存在状态转移中的幻觉问题（Kalai et al., 2025; Wang et al., 2024）。对于 RL 而言，它成本高昂且效率低下，因为每个环境步骤都可能需要调用一次 LLM。基于编程的合成通过编程和数据库构建环境，其中每个状态转移和观察都由代码驱动。一些方法从文档中提取工具图并采样工具调用序列来构建环境（Fang et al., 2025; Cai et al., 2025）。程序化生成也已被探索，例如使用人工设计的类型系统（Sullivan et al., 2025）。AutoEnv（Zhang et al., 2025a）创建了 36 个类游戏环境（例如，迷宫导航）来模拟异构世界。EnvScaler（Song et al., 2026）是一项并行工作，它在给定现有任务集的情况下，通过代码生成合成了 191 个交互式环境。

**所提出的 AWM（Agent World Model）在三个方面有所不同** ：(1) 我们 **从零开始合成环境** ，不假设预定义的任务集或 API 文档。这避免了人为先验，并实现了可扩展的合成。(2) 我们使用 **基于数据库的状态管理** 来强制一致性，并为 RL 实现代码增强的验证。(3) 据我们所知，AWM 合成了 1,000 个环境、35,062 个工具以及 10,000 个配有验证代码的任务，是迄今为止 **最大的开源工具使用环境集** 。

## 3 智能体世界模型（Agent World Model）

本节将详细描述 AWM，如图 [2](#figure-2) 所示。我们将环境合成为适用于智能体强化学习训练的 **部分可观测马尔可夫决策过程（Partially Observable Markov Decision Processes, POMDPs）** 。每个环境 $E_{i}$ 包含五个组成部分：一个状态空间 $\mathcal{S}_{E_{i}}$、一个动作空间 $\mathcal{A}_{E_{i}}$、一个观察空间 $\mathcal{O}_{E_{i}}$、一个转移函数 $T_{E_{i}}:\mathcal{S}_{E_{i}}\times\mathcal{A}_{E_{i}}\rightarrow\mathcal{S}_{E_{i}}\times\mathcal{O}_{E_{i}}$，以及针对环境中任务集 $\mathcal{T}_{E_{i}}$ 中每个任务 $\tau$ 的特定任务奖励函数 $R_{\tau}$。智能体的目标是通过多轮工具交互与环境互动以完成任务。第 [3.3.1](https://arxiv.org/html/2602.10090v2#S3.SS3.SSS1) 节中的合成流程将实例化：数据库定义 $\mathcal{S}_{E_{i}}$，接口层定义 $\mathcal{A}_{E_{i}}$、$\mathcal{O}_{E_{i}}$ 和 $T_{E_{i}}$，而验证则为每个用户任务提供 $R_{\tau}$。

### 3.1 场景生成（Scenario Generation）

我们利用现代 LLMs 的广阔世界知识，以 100 个热门领域名称为种子，生成多样化的场景描述（网站、应用程序或常用工具集合）。与浏览静态内容站点（例如新闻、维基）的通用网络智能体不同，我们 **专注于需要进行数据库交互而非信息检索的有状态应用程序** （例如电子商务、客户关系管理、管理系统）。为确保质量，我们采用了一个过滤流程：一个基于 LLM 的分类器筛选涉及核心 CRUD 操作（创建、读取、更新、删除）的场景，同时基于嵌入的去重确保多样性。我们还对过度代表的类别设置上限，以防止集合坍缩为少数主导类型。此过程产生了 1,000 个独特的场景，涵盖金融、旅游、零售、社交媒体等领域，如图 [7](https://arxiv.org/html/2602.10090v2#A2.F7) 和表 [9](#table-9) 所示。

<a id="section-3-2"></a>

### 3.2 任务生成（Task Generation）

遵循软件工程原则，我们随后合成用户任务，作为环境的功能需求。这些任务将决定后续合成步骤中必要的数据库实体和 API 端点。对于每个场景，我们提示 LLM 生成 $k=10$ 个不同的任务 $\mathcal{T}_{E_{i}}=\{\tau_{i,j}\}^{k}_{j=1}$，覆盖该场景的多样化功能。我们强制执行两个设计原则：(1) **API 可解性** ，避免纯粹依赖用户界面的操作（例如点击、页面导航）；(2) **认证后上下文** ，假设登录已完成，以专注于深层功能而非访问控制，因为在现实设置中此类认证通常由人类处理。这产生了 10,000 个可执行任务，将驱动环境后端的合成。

<a id="section-3-3"></a>

### 3.3 环境合成（Environment Synthesis）

给定一个场景描述及其任务集 $\mathcal{T}_{E_{i}}$，我们通过实例化 POMDP 组件来合成一个可执行环境 $E_{i}$。首先，我们通过生成一个 SQLite（Gaffney et al., 2022）模式并用支持 $\mathcal{T}_{E_{i}}$ 所隐含的实体和约束的合成样本数据填充它，来构建状态空间 $\mathcal{S}_{E_{i}}$ 和初始状态。然后，我们生成一个 MCP（Anthropic, 2024）接口层，以 Python 形式公开一个工具集，该接口层将动作空间 $\mathcal{A}_{E_{i}}$ 定义为工具调用，将观察空间 $\mathcal{O}_{E_{i}}$ 定义为工具响应。调用工具会执行读写数据库操作，从而实现环境转移函数 $T_{E_{i}}$。最后，我们合成验证逻辑来定义特定任务的奖励函数 $R_{\tau}$。这种设计将环境状态建立在结构化数据中，同时确保智能体仅通过统一的 MCP 接口与 $E_{i}$ 交互。

- [3.3.1 环境（Environment）](#331-environment)
- [3.3.2 流程结果与分析（Pipeline Results and Analysis）](#332-pipeline-results-and-analysis)

#### 3.3.1 环境（Environment）

**数据库（Database）** 。数据库将每个环境建立在具体且持久的状态中。我们使用 SQLite（Gaffney et al., 2022）作为结构化关系状态的后端，这与并行工作中使用的简化 NoSQL 或键值存储不同（Zhang et al., 2025a; Cai et al., 2025; Song et al., 2026）。给定场景和任务集 $\mathcal{T}_{E_{i}}$，LLM 推断出使每个任务可行所需的实体/属性/关系，仅在任务需要时生成表。我们排除了与认证相关的字段，以与任务生成步骤保持一致。模式定义了状态空间 $\mathcal{S}_{E_{i}}$，并通过显式键和约束限制所有状态转移。然而，仅有模式是不够的，因为许多任务需要查询或更新现有记录。因此，我们合成了样本数据，实例化一个现实的初始状态 $s_{0}$，确保 $\mathcal{T}_{E_{i}}$ 中的每个任务从一开始就是可执行的。LLM 分析每个任务的前提条件，并创建满足这些约束的记录，包括鲁棒执行所需的变体数据。

**接口（Interface）** 。智能体无法在不破坏抽象的情况下直接操作数据库。我们引入了一个通过 **模型上下文协议（Model Context Protocol, MCP）** (Anthropic, 2024) 暴露的 Python 接口层，该层定义了动作空间 $\mathcal{A}_{E_{i}}$ 和观察空间 $\mathcal{O}_{E_{i}}$。我们采用两个阶段：首先是工具集模式设计，然后是代码生成。初步实验表明，环境可能需要超过 3000 行代码，这使得在没有模式指导的情况下直接生成具有挑战性。给定任务集和数据库模式， **大型语言模型（Large Language Model, LLM）** 推断出使每个任务可执行所需的最小操作集合，仅在必要时生成端点。该模式还通过摘要、类型化参数和响应模式，作为智能体的文档，如表 [B.2](https://arxiv.org/html/2602.10090v2#A2.SS2) 所示。然后，我们生成一个可执行的 Python 文件，其中每个端点成为一个 MCP 工具。工具执行会触发数据库操作，从而实现转移函数 $T_{E_{i}}$。

**验证（Verification）** 。为了完成 **部分可观测马尔可夫决策过程（Partially Observable Markov Decision Process, POMDP）** 的规范定义，我们定义任务特定的奖励函数 $R_{\tau}$ 以支持 **强化学习（Reinforcement Learning, RL）** 训练。我们为每个任务 $\tau$ 设计了一个与任务关联的验证模块，该模块将评估基于环境状态进行。具体来说，该模块检查智能体执行前后的数据库状态，提取与任务相关的信号以及描述如何解释状态差异的成功或失败标准。然而，由于我们的环境是完全合成的，验证偶尔会受到环境不完善的影响，例如不完整的状态更新、意外的执行失败或与基础设施相关的问题（例如，超时）。为了提高奖励的鲁棒性，最终决策由一个 **LLM 即法官（LLM-as-a-Judge）** (Zheng et al., 2023) 做出，该法官将智能体轨迹与结构化验证信号相结合。LLM 即法官通过利用轨迹级别的上下文来补充基于代码的检查，这有助于减轻由不完善的环境信号引起的误判。最后，验证步骤返回 {已完成（Completed）、部分完成（Partially Completed）、智能体错误（Agent Error）、环境错误（Environment Error）} 中的一种。

一个自然的问题是： **为什么不完全依赖代码驱动的验证？** 虽然这种方法很有吸引力，但它假设任务成功是完全可以指定并且仅从状态就能可靠观察到的。在实践中，这个假设是脆弱的。即使是现实的服务也会由于瞬时故障、部分执行或基础设施问题而表现出不完美的行为；合成环境也不例外。在一般的任务设置中，脆弱的验证逻辑可能会引入误报或漏报，这个问题在现有基准测试中反复出现，如 WebArena、$\tau^{2}$-bench 和 SWE-Bench，这些基准后来都进行了修订以纠正早期的误判 (hattami et al., 2025; Cuadron et al., 2025; OpenAI, 2024)。我们 **基于代码增强的 LLM 即法官** 通过结合基于代码验证的精确性和 LLM 推理的灵活性及上下文感知能力来解决这个问题。具体来说，结构化验证信号将 LLM 基于具体证据，使其能够解决仅靠僵化的代码无法处理的模糊情况。我们也为 AWM 准备了代码驱动的验证，为社区提供两种选择，尽管我们在第 [6.2](#section-6-2) 节的分析和附录 [B.2](https://arxiv.org/html/2602.10090v2#A2.SS2) 中对验证失败案例的研究证实，基于代码增强的 LLM 即法官更加鲁棒。

**基于执行的自校正（Execution-based Self-Correction）** 。在上述所有合成步骤中，我们采用了一种简单的自校正机制来处理生成错误。在生成环境的每个组件后，我们尝试在隔离环境中运行并测试其功能。如果发生任何错误（例如，运行时异常），我们会捕获错误消息并将其与有问题的代码片段一起反馈给 LLM，提示 LLM 重新生成一个修正版本。此过程最多重复五次迭代，或直到组件成功执行为止。在实践中，我们经常发现这种轻量级的重试策略在修复生成的代码方面是有效的，无需更复杂的校正机制。

## 4 智能体强化学习 (Agentic Reinforcement Learning)

利用合成的环境，我们使用 **组相对策略优化（Group Relative Policy Optimization, GRPO）** (Shao et al., 2024) 为工具使用智能体执行在线强化学习。智能体交互涉及长视野的轨迹，其中观察和工具调用交错进行，这既需要仔细的奖励设计，也需要训练与推理之间的一致性。

- [4.1 奖励设计](#41-reward-design)
- [4.2 历史感知训练](#42-history-aware-training)

<a id="section-4-1"></a>

### 4.1 奖励设计 (Reward Design)

纯基于结果的奖励在数学推理中已显示出成功 (Guo et al., 2025)；然而，在智能体环境中，它们可能不足以且效率低下地规范工具使用行为。因此，我们采用了一种混合奖励设计，将步骤级别的格式正确性与任务级别的结果验证相结合。在每个步骤 $t$，我们检查工具调用是否遵循所需的格式（见附录 [A.4](https://arxiv.org/html/2602.10090v2#A1.SS4)）。任何违规都会触发 **回合（rollout）** 的提前终止和立即的负奖励。这既阻止了无效动作，又在长视野多轮设置中节省了计算量。当回合正常终止后，我们通过基于代码增强的 LLM 即法官评估任务级别的结果，将最终奖励定义为：

$$
R_{\tau}=\left\{\begin{array}[]{@{}l@{\,}l@{}}1.0,&\text{如果任务}\tau\ \texttt{已完成（Completed）},\\ 0.1,&\text{如果任务}\tau\ \texttt{部分完成（Partially Completed）},\\ 0.0,&\text{其他情况}.\end{array}\right.(1)
$$

步骤级别的奖励 $r_{t}$ 遵循：如果在步骤 $t$ 发生提前终止，则 $r_{t}=-1.0$；如果回合正常终止，则 $r_{t}=R_{\tau}$ 广播到所有动作步骤；否则 $r_{t}=0$。这种设计鼓励语法上有效的工具使用，同时保留结果驱动的优化。

<a id="section-4-2"></a>

### 4.2 历史感知训练 (History-Aware Training)

在部署智能体时，历史上下文通常由专用框架管理，该框架策略性地截断长交互历史以避免注意力下沉并提高效率 (Liu et al., 2024a; Anthropic, 2025b; Zhang et al., 2025b)。然而，现有的 RL 训练流程可能会使用完整历史来优化策略，从而在训练和推理之间造成分布不匹配问题。

令 $h_{t}=(o_{1},a_{1},o_{2},a_{2},\ldots,o_{t})$ 表示完整的交互历史。在实践中，许多 RL 框架 (Sheng et al., 2024; Hu et al., 2025) 为了提高效率，在一个模型前向传递中优化来自已完成回合的所有动作：

$$
\begin{split}\mathcal{L}=&-r\log\pi_{\theta}(\underbrace{o_{1},a_{1},o_{2},a_{2},\ldots,o_{T},a_{T}}_{\text{一次前向传递}})\\ &\cdot\underbrace{[0,1,0,1,\ldots,0,1]}_{\text{损失掩码}},\end{split}(2)
$$

其中 $\pi_{\theta}$ 是由 $\theta$ 参数化的智能体，掩码选择动作标记而忽略观察。然而，在推理时，智能体可能基于截断的历史 $h_{t}^{\text{trunc}}=(o_{\max(1,t-w+1)},a_{\max(1,t-w+1)},\ldots,o_{t})$ 进行条件化，如果训练总是使用完整历史，这会导致分布偏移。为了解决这个问题，我们在优化过程中应用相同的截断，使训练与推理保持一致。在 GRPO 下，对于环境 $E_{i}$ 中的每个任务 $\tau$，我们采样一组 $G$ 条回合轨迹 $\{y^{(k)}\}_{k=1}^{G}$，其中 $y^{(k)}=(a_{1}^{(k)},\ldots,a_{T_{k}}^{(k)})$，并优化：

$$
\displaystyle\mathcal{L}_{\text{GRPO}}=\mathbb{E}_{\tau,E_{i},\{y^{(k)}\}}\left[\frac{1}{G}\sum_{k=1}^{G}A^{(k)}\sum_{t=1}^{T_{k}}\log\pi_{\theta}(a_{t}^{(k)}\mid h_{t}^{\text{trunc},(k)})\right],(3)
$$

其中 $A^{(k)}=(R^{(k)}-\bar{R})/\sigma_{R}$ 是根据回合奖励 $\{R^{(j)}\}_{j=1}^{G}$ 计算得出的组相对优势。这个目标将轨迹分割成多个独立的子轨迹，每个子轨迹以其自身的截断历史为条件，确保与推理时执行的一致性。

### 5.1 实验设置（Experimental Setup）

**基准测试（Benchmarks）。** 我们在三个工具使用和多服务器控制协议（Model Context Protocol, MCP）基准测试上评估智能体，以评估其分布外泛化能力：

1.  $\tau^{2}$-bench 的已验证版本（Barres 等人，2025；Cuadron 等人，2025），包含跨三个代表性场景（航空、零售和电信）的多轮对话式智能体任务。
2.  BFCLv3（Patil 等人，2025），一个用于评估函数调用能力的综合性基准，涵盖单轮、多轮（长上下文）、合成工具、真实世界工具和幻觉测试，最终形成四个评估类别：非实时（non-live）、实时（live）、多轮（multi-turn）和幻觉（hallucination）。
3.  MCP-Universe（Luo 等人，2025），一个涵盖位置导航、金融分析、浏览器自动化、网络搜索和多服务器工作流的真实世界 MCP 服务器集合。我们排除了需要图形用户界面（GUI）的 3D 设计任务以及需要对 GitHub 或 Notion 进行身份验证访问的仓库管理任务。

**基线模型（Baselines）。** 我们与以下基线进行比较：

1.  **基础模型（Base）** ：具备推理和工具使用能力但未经额外训练的原始大型语言模型（LLMs）。
2.  **模拟器（Simulator）** （Li 等人，2025b；Chen 等人，2025）：在 LLM 模拟环境中使用强化学习（Reinforcement Learning, RL）训练的智能体，其中 GPT-5（OpenAI，2025）作为环境转移模型，使用与 AWM 相同的任务和工具集，以突显可执行环境相较于模拟环境的优势。
3.  **环境缩放器（EnvScaler）** （Song 等人，2026）：一种并行方法，合成了 191 个基于编程的环境用于监督微调（Supervised Fine-Tuning, SFT）和 RL，纳入比较以评估合成质量。

**实现细节（Implementation Details）。** AWM 流程使用 GPT-5（OpenAI，2025）实例化，该模型也用作任务验证的代码增强型 LLM 即法官（LLM-as-a-Judge）。我们选择 Qwen3 思维模型（Yang 等人，2025）的 4B、8B 和 14B 规模作为基础智能体，因其在社区中被广泛采用。多轮 RL 训练在 AgentFly（Wang 等人，2025a）和 verl（Sheng 等人，2024）框架上实现。由于计算资源有限，我们在 AWM 的一个子集（包含 526 个环境和 3,315 个任务）上训练智能体。每个模型最多训练 96 个优化步，固定学习率为 $7\times 10^{-7}$。我们使用批次大小为 64 和 16 次并行采样，导致每步启动 1,024 个独立环境实例。滑动窗口大小和最大交互轮数分别设置为 $w=3$ 和 $20$。更多细节见附录 [A](#appendix-a)。

## 7 结论（Conclusion）

在本文中，我们提出了 **智能体世界模型（Agent World Model, AWM）** ，这是一个通过模拟实际软件开发来合成可执行智能体环境的可扩展流程。利用 AWM，我们成功扩展到 1,000 个环境，包含 35,062 个工具和 10,000 个任务。这些环境是代码驱动的，并由通过统一 MCP 接口暴露的 SQL 数据库支持，为大规模智能体强化学习提供并行隔离实例。在三个基准测试上的实验表明，在我们的合成环境上训练的智能体能够很好地泛化到分布外领域，其性能优于 LLM 模拟训练和并发合成方法。我们相信 AWM 的 1,000 个合成环境及其可扩展流程是社区宝贵的资源。

## 影响声明（Impact Statement）

这项工作提出了一个用于合成可执行环境以训练工具使用智能体的开源流程。通过发布生成流程和合成环境，我们旨在降低研究社区研究智能体系统的门槛。然而，合成环境可能无法完全反映现实世界场景，因此我们鼓励社区在将基于 AWM 训练的智能体部署到现实场景时应用安全防护措施。

## 局限性（Limitations）

**自我演化的机会** 。我们的 AWM 流程通过固定的生成过程合成环境，这固有地限制了模型自主改进和超越初始能力演化的能力。虽然这种方法在我们的实验中显示出改进，但整合一种自我演化范式，让训练好的智能体参与合成新环境，可以使模型持续适应并提升其能力。我们将此留作未来工作的一个有前景的方向。

**合成流程优化** 。当前的 AWM 流程存在进一步优化的机会。例如，自我纠正目前主要通过试错进行，解决运行时错误而缺乏更深层的语义验证。集成一个 LLM 来主动检测运行时检查未捕获的逻辑不一致性或细微错误，可以增强生成环境的鲁棒性和语义连贯性。如果资源允许，进行人工检查以进一步提高合成环境的质量也很有价值。此外，合成跨越多个场景或环境的任务是另一个有前景的扩展领域。这两项增强都易于与我们现有的架构兼容，为未来改进提供了清晰的路径。

**训练规模和模型覆盖范围** 。由于计算资源有限，我们在 1,000 个合成环境中的 526 个上训练智能体。我们也主要关注 Qwen3 模型系列（Yang 等人，2025）的 4B、8B 和 14B 规模。尽管存在这些限制，实验已经证明了在三个基准测试上一致的分布外泛化能力，表明即使是 AWM 的一个子集也能提供强大的训练信号。重要的是，本文的核心贡献是合成流程本身。发布的环境和流程与模型无关，无论我们实验中使用的具体模型是什么，都能使更广泛的社区受益。
